############################################################
CONNECTION REDUNDANCY: extra full-relay vs extra full-recon
############################################################

Hypotheses under test
---------------------
H1a  Adding N extra outbound-full-relay connections to already well-connected
     nodes reduces latency at the cost of adding mostly redundant traffic
H1b  Adding N extra outbound-full-recon connections should keep latency almost
     constant, but not have a relevant effect on bandwidth
H2   On those extra recon links the exchanged sketches almost always decode on
     the first try (sets nearly identical), so extension should be rare

Setup
-----
Networks (all 100 nodes, 30 reachable, seed 1337, image
srgi/bitcoin:99.0.0-erlay-full-recon-d2f8, txreconciliation=1):
  control : 8 outbound-full-relay per node (addnode baseline only)
  relay   : baseline + 4 extra outbound-full-relay per node (addconnection)
  recon   : baseline + 4 extra outbound-full-recon  per node (addconnection)
The three share an identical base network (addnode), relay and recon only differ
in the type of the extra (400) edges.

Command per arm:
```
  warnet deploy networks/conn-redundancy-<arm>
  warnet run scenarios/check_net_bandwidth.py --tx_count=50 --n=5
```

RESULTS
============================================================

H1a  Hypothesis confirmed: ~43% increase in redundant INV traffic, ~33% latency reduction.
H1b  Hypothesis confirmed: latency ~6% slower, ~2% traffic increase (reconciliation overhead)
H2   Reconciliation params may need tweaking: ~82% of reconciliations without extensions
