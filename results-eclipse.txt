############################################################
SINGLE-NODE ECLIPSE: do extra connections save a victim?
############################################################

Hypothesis
----------
A node whose entire baseline outbound (8 full-relay slots) is captured by an
attacker is fully eclipsed and receives no blocks or transactions. A handful 
of extra honest connections are the lifeline that defeats the eclipse.

This is the adversarial equivalent of the connection-redundancy experiment: the same
extra connections are now the victim's only path out of an eclipse.

Setup
-----
100 nodes, generated by utils/create_eclipse_network.py --honest 91 --reachable 27
(image srgi/bitcoin:99.0.0-erlay-full-recon-blackholes-5ea9, txreconciliation=1):
91-node random honest mesh (create_network.py) + 8 blackholes + 1 victim, in
networks/eclipse-{control,relay,recon}. Only 27 of the 91 honest nodes are
reachable nodes. The experiment runs 3 arms:

  control : 8 full-relay                         (all nodes: 8 outbound)
  relay   : 8 full-relay + 4 extra full-relay     (all nodes: 12 outbound)
  recon   : 8 full-relay + 4 extra full-recon     (all nodes: 12 outbound)

The victim's 8 baseline outbound (manual) go to the 8 blackholes in every arm.
Its 4 extra connections (addconnection) go to random reachable honest nodes.

Results
-------

  CONTROL (0 honest lifeline / 8 blackhole baseline)
    transactions received : 0 / 20
    time to receive all   : never (timeout)
    post-eclipse block    : eclipse 120/121
    bytes received / msg  : addrv2/ping/pong only (no inv/tx/block/sketch)

  +4 FULL-RELAY (4 honest full-relay lifeline / 8 blackhole baseline)
    transactions received : 20 / 20
    time to receive all   : 2.4 s
    post-eclipse block    : 121/121 (synced)
    bytes received / msg  : inv 742, cmpctblock 279, headers 103, tx 4860

  +4 FULL-RECON (4 honest full-recon lifeline / 8 blackhole baseline)
    transactions received : 20 / 20
    time to receive all   : 18.7 s
    post-eclipse block    : 121/121 (synced)
    bytes received / msg  : inv 742, sketch 34, cmpctblock 279, headers 103, tx 4860

============================================================
Results
============================================================

The baseline branch is eclipsed, while both relay and recon branches
survive the eclipse (as expected).

Reconciliation takes significantly longer to propagate the transaction than
fanout (2.4s vs 18.7s). Higher latency is not an issue here: the goal is surviving
the eclipse while maintaining an almost constant bandwidth and latency during normal operation mode.

No relevant advantage for the victims bandwidth either: same amount of invs and transactions, the additional
overhead of sending one sketch.
